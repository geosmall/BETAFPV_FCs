# Pavo Pico II Betaflight 4.5.0 → 2026.6 Autotune Upgrade

**Aircraft:** BETAFPV Pavo Pico II, 2S, DJI O4 configuration  
**Flight controller:** BETAFPV F405 2–3S 20A V1.0  
**Target:** `BETAFPVF405`  
**Gyro/accelerometer:** ICM42688P (per the aircraft's own 4.5.0 `status`; see §10)  
**Starting firmware verified on aircraft:** Betaflight 4.5.0 (`c155f5830`, Dec 25 2024)  
**Upgrade target for this procedure:** Betaflight **2026.6.1** (released 2026-08-02)  
**Document date:** 2026-08-07

---

## 1. Purpose

This procedure migrates a known-airworthy Pavo Pico II from the BETAFPV/OEM Betaflight 4.5.0 configuration to Betaflight 2026.6 so the aircraft can use the new CHIRP/sysid-based Autotune workflow.

The upgrade is intentionally divided into two flight phases:

1. **Phase 1 — Airworthiness and stability**
   - Clean firmware flash.
   - Rebuild only the configuration required to reproduce a safe, known-good aircraft.
   - Fly normally.
   - Verify orientation, receiver, motors, OSD, failsafe behavior, control stability, temperatures, and Blackbox logging.
   - **Do not use CHIRP yet.**

2. **Phase 2 — SysID / Autotune**
   - Enable and assign CHIRP.
   - Record controlled CHIRP flights in Blackbox.
   - Analyze those logs in the Betaflight 2026.6 Autotune tab.
   - Review recommendations before applying them.
   - Re-flight-test any changed tune.

The goal is to avoid changing firmware, filtering, PID behavior, and system-identification excitation all at once.

---

## 2. Important status and cautions

This procedure uses **Betaflight 2026.6.1**, released **2026-08-02**.

Therefore:

- Preserve a complete rollback path before flashing.
- Do not blindly paste a Betaflight 4.5 `dump` or `diff` into 2026.6.1.
- Re-create configuration deliberately.
- Remove props for all bench motor tests.
- Do not use CHIRP until Phase 1 is complete.
- Do not enable the experimental `AUTOPILOT` function on a real aircraft. It is unrelated to this procedure and Betaflight documents it as simulation-only.

## 18. Re-create motor / ESC settings

Use the motor/ESC values from **that aircraft's own saved pre-upgrade configuration**.

For the verified reference aircraft, they were:

```text
set dshot_idle_value = 1150
set dshot_bidir = ON
set motor_pwm_protocol = DSHOT300
set motor_poles = 12
set motor_output_reordering = 2,3,0,1,4,5,6,7
```

Verify the actual aircraft's values in its saved `diff all` / `dump all`, and verify that the equivalent parameters still exist before applying them.

**Parameter rename:** 4.5's `dshot_idle_value` was renamed `motor_idle` in 2026.x (same units, 0.01%; default 550 = 5.5%). Pasting the old name fails silently inside a batch, leaving the aircraft at half the OEM idle — this actually happened during the first pass of this upgrade and was only caught by inspecting the post-flash `dump all`.

**Outcome:** this aircraft then flew Phase 1 and the full CHIRP campaign at the 550 default without issue, so **550 is the adopted value**. The OEM 4.5 value (1150) remains the fallback if low-throttle authority or descent-desync problems ever appear.

After pasting any migrated block, re-run `diff all` and confirm every intended non-default value actually appears.

Do **not** switch to DSHOT600 merely because a generic cinewhoop preset uses it.

The OEM aircraft is proven on DSHOT300.

3. Hover low.

## 34. Immediate post-hover inspection

Check:

- Motor temperatures by touch or measurement.
- FC/ESC temperature if available.
- Unusual oscillation.
- Audible high-frequency motor noise.
- Motor desync symptoms.
- Unexpected yaw.
- Bounce-back.

# PART H — PHASE 2: CHIRP / SYSID / AUTOTUNE

## 38. What Betaflight 2026.6 Autotune does

Betaflight 2026.6 introduces an experimental, file-based Autotune workflow.

The aircraft records a Blackbox log containing CHIRP excitation. The Autotune tab then:

- identifies CHIRP regions using the `BOXCHIRP` flight-mode bit;
- estimates the closed-loop frequency response;
- uses Welch-based analysis;
- evaluates bandwidth;
- evaluates phase margin;
- evaluates resonant peak;
- evaluates noise floor;
- recommends Simplified Tuning slider values.

The analysis can be performed without an FC connected.

When an FC is connected, **Apply Gains** can write the recommended simplified tuning values via MSP.

Recommendations must still be engineering-reviewed before use.

---

- Blackbox feature enabled.
- Suitable onboard storage selected.
- Sufficient free space.
- Logging starts reliably.
- A test arm/disarm produces a downloadable log.

Erase old flash only after important Phase 1 logs have been saved.

Do not begin a CHIRP flight if Blackbox storage is nearly full.

## 42. CHIRP flight environment

Use:

- a large open flying area;
- low wind;
- good visibility;
- adequate altitude and clearance;
- a healthy fully charged 2S battery;
- no nearby people or obstacles.

Do not conduct the first CHIRP test indoors or in a constrained room.

The excitation is intentionally designed to perturb the control system.

---

## 43. First CHIRP flight sequence

Use this conservative progression:

1. Take off normally with CHIRP **OFF**.
2. Establish a stable hover / low-speed flight condition.
3. Verify the aircraft feels identical to the successful Phase 1 configuration.
4. Move to an area with ample clearance.
5. Activate CHIRP only for the intended identification interval.
6. Maintain enough altitude to recover from unexpected motion.
7. Deactivate CHIRP.
8. Return to normal flight.
9. Land.
10. Disarm.
11. Wait for Blackbox storage to finish writing before removing power.

If behavior becomes unexpected, disable CHIRP immediately and land.

---

## 44. Post-CHIRP physical inspection

Before running another CHIRP:

- check all four motor temperatures;
- inspect props;
- inspect ducts;
- inspect motor screws;
- inspect battery condition;
- note any unusual sound or oscillation.

A sysid maneuver should never be used to “push through” evidence of an unstable or thermally stressed aircraft.

---

## 45. Save the CHIRP log

Download the Blackbox log and save it with an unambiguous name, for example:

```text
Phase2_Autotune/logs/
PavoPicoII_BF2026.6.1_CHIRP_01.bbl
```

Do not erase the flash until the log has been verified readable.

---

## 46. Analyze in the Autotune tab

Enable Expert Mode if required.

Open:

```text
Autotune
```

Load the CHIRP Blackbox log.

Verify that the application identifies the CHIRP segment(s).

Review:

- frequency-response plots;
- bandwidth;
- phase margin;
- resonant peaks;
- noise floor;
- proposed simplified slider changes;
- proposed D-term filtering changes.

Do **not** immediately click Apply Gains merely because a result was generated.

---

## 47. Engineering review of recommendations

Compare Autotune recommendations against the proven Phase 1 baseline:

| Parameter | Phase 1 baseline | Autotune |
|---|---:|---:|
| Master | 125 | ___ |
| I | 70 | ___ |
| D | 135 | ___ |
| PI | 100 | ___ |
| D Max | 0 | ___ |
| Feedforward | 45 | ___ |
| Pitch D | 120 | ___ |
| Pitch PI | 115 | ___ |

Large deviations require explanation from the measured response.

Pay particular attention to:

- large increases in D;
- large reductions in filtering;
- recommendations that materially change the OEM roll/pitch balance;
- unusually high master multiplier;
- changes that are inconsistent between repeated CHIRP runs.

Betaflight 2026.6 includes a safety fix preventing Autotune from recommending less D-term filtering than is currently configured, but that does not remove the need for review.

---

## 48. Prefer repeatability over a single result

For engineering use, perform more than one valid CHIRP flight when practical.

A strong result is one where:

- repeated flights produce broadly similar identified response;
- recommended sliders converge;
- no anomalous noise/oscillation appears;
- motor temperatures remain acceptable.

Treat a single outlying recommendation as suspect until repeated.

---

## 49. Applying an Autotune recommendation

Before applying:

```text
diff all
```

and save the pre-change file.

Then either:

1. use **Apply Gains** in Autotune, or
2. enter the reviewed simplified parameters manually.

Immediately afterward save:

```text
diff all
get simplified
```

as the candidate tune configuration.

---

# PART I — POST-AUTOTUNE FLIGHT TEST

## 50. Treat the recommended tune as a new test configuration

An Autotune recommendation is not automatically production-qualified.

Repeat the Phase 1 progression:

1. props-off sanity check;
2. short hover;
3. motor-temperature check;
4. gentle normal flight;
5. Blackbox review;
6. progressively more representative flight.

Do not go directly from Apply Gains to aggressive flight.

---

## 51. Acceptance criteria for the tuned configuration

Accept the candidate only if it provides:

- stable hover;
- good setpoint tracking;
- no unacceptable high-frequency oscillation;
- no excessive propwash oscillation;
- no objectionable bounce-back;
- acceptable motor/ESC temperatures;
- no motor desync;
- acceptable flight feel;
- repeatable Blackbox behavior.

If the Autotune result is worse than the Phase 1 tune, revert and investigate rather than accepting the result automatically.

---

# PART J — ROLLBACK

## 52. Roll back the 2026.6 tune only

If firmware operation is good but the candidate tune is not:

- restore the saved Phase 1 2026.6 `diff`;
- confirm orientation/motors/modes;
- repeat a short hover.

---

## 53. Full rollback to OEM 4.5

If the 2026.6 firmware itself proves unsuitable:

1. Flash the preserved OEM/known-good 4.5 firmware.
2. Use Full Chip Erase as appropriate.
3. Restore the saved matching 4.5 configuration.
4. Re-verify:
   - gyro;
   - board orientation;
   - motor numbering;
   - motor direction;
   - receiver;
   - modes;
   - OSD;
   - failsafe.
5. Perform a short validation hover.

Never restore a 4.5 dump directly onto 2026.6 or vice versa.

## Revision note

This document includes values from one actual pre-upgrade Pavo Pico II `diff all` as a reference, but the procedure requires each aircraft to save and use **its own** complete pre-upgrade `4.5.0/cli.txt` transcript containing `diff all` and `dump all`. The reference values must never be treated as a fleet-wide replacement configuration.

Because Betaflight 2026.6 can still differ from 4.5 in parameter names and behavior, verify commands against the exact 2026.6.1 firmware build before pasting CLI blocks. Where this document says to run `get ...` first, that verification is intentional.
